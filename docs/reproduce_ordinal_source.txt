Ordinal GTA source release: scope and local source export

This source-only version changes the fixed consumer of the existing five-class
radius composition: c=p1+(2*p2+p3)/3. The constant arm consumes .4 from the
same uniform-five-class vector. Both retain G0, the original attribute heads,
auxiliary weights .1/.1, the same256 signed interaction parameters and GDF0.
The scalar is ordinal fineness, not a diameter or a clinical label. Empty and
>8mm classes both contribute0. This is a bounded AVT instance of GTA's
attribute -> condition -> feature-adaptation design hypothesis.

Private executed36 and public mapped36 have separate identities. The ordinal
model and synthetic-check source bytes are identical. One older public
mechanism file already uses a generic output-origin label; the new public
trainer updates only that file's expected source hash. No model, loss, sampler
or optimizer arithmetic changes. See next_stage/ordinal_source_identity_20261023.json.
Private GPU engineering success does not certify the mapped public36 source.
No public-source GPU QA, training or dynamic-efficacy result is claimed here.

The public checkout contains additional studies. Isolate exactly36 sources:

  python tools/export_ordinal_source.py --project .

Default performs source binding and a metadata plan only. It reads source
bytes, not patient data, checkpoints or a GPU. To create a new isolated folder:

  python tools/export_ordinal_source.py --project . --output work/ordinal36 --execute

The folder contains exactly36 scientific files. Its sibling
work/ordinal36_source_manifest.json retains the exact public manifest bytes;
work/ordinal36_export_receipt.json certifies only source binding. It is never
a passed model/data/runtime preflight. --overlay may supply only the three
new ordinal files when reviewing a source overlay before publication.

Reference recipes are configs/ordinal_C_ord.json and ordinal_D_ord.json. C_ord
means the constant arm and D_ord means the dynamic arm, independent of any
block label. Both recipes have one matching finetuning/augmentation seed.
The existing trainer permits the three frozen seeds20261024/25/26. Source
export does not launch them. Example inert trainer plan, using a genuine
local cache manifest path when later running the experiment:

  python work/ordinal36/next_stage/ordinal_stage_train.py --config configs/ordinal_C_ord.json --manifest cache/manifest.json --output runs/ordinal_C

That default does not open the data manifest or launch training. Actual
execution retains strict prerequisites: the genuine common tensor-only
warmstart with its declared7406... SHA, matching public36 source map, new
actual CUDA128/B2 AMP model QA, full input-byte audit, and passed prospective
TRAIN attribute/geometry gates bound to the actual source/data/runtime. The
trainer refuses missing or stale receipts. Private deployment controllers,
server credentials/paths and historical runtime receipts are not distributed.
A source-export receipt cannot substitute for any prerequisite; do not invent
a passed preflight or reuse private receipts for the mapped public version.
This release supplies source and inert reference plans, not a newly certified
public end-to-end launch workflow.

The private ordinal study is still judged using its frozen prospective
protocol: both utility and correct-correspondence tests are required. Attribute
predictability, parameter updates, syntactic checks and source export alone
do not establish useful dynamic conditions, zero-shot transfer or low variance.
No checkpoint, data, manuscript, server operation or new evaluation is included.
